# 펫 견적 대화의 조사·검증

## 실행 경로

1. 현재 문의로 외부 기술 사실을 확인할 필요가 있는지 계획한다. 사용자 원문을 검색 서비스에 전송하지 않는다. 검색어는 등록된 공개 기술명·기술 주제로 다시 제한한다.
2. 설정된 Tavily 검색기가 있으면 허용 도메인 검색·본문 조회를 사용한다. 없으면 등록된 공식 문서 라이브러리(Stripe, Slack, Next.js, W3C, PostgreSQL, OWASP)에서 관련 문서를 직접 조회한다. 라이브러리에 없는 기술은 조사했다고 하지 않는다.
3. 펫 1~3마리가 같은 출처 목록과 이전 발화를 보며 순서대로 답한다. 공수는 가정을 설명하며, 금액은 기존 견적 서버가 계산한다.
4. 작성자의 역할·합의와 분리된 새 모델 호출이 원문 요구사항, 전체 교체 초안, 각 발화와 수집 본문을 검토한다. 선택한 모델은 유지한다. 서로 다른 모델을 이용한 교차 검증은 아니다.
5. 검토자가 제출한 원문 인용, 요구사항→견적 항목 연결, 모든 항목의 공수 검사, 모든 발화 검사, 발화/항목별 출처 인용과 본문 발췌를 서버가 다시 확인한다. 누락·근거 부족·비현실적 공수·검증 실패가 있으면 제안 반영을 차단한다. 발화와 보완 사항은 남긴다.
6. 사용자가 검토를 통과한 제안을 반영하고 견적 화면에서 저장한다. 저장 금액은 서버 미리보기와 동일한 계산 경로를 유지한다.

새 공수는 대상 규모 가정과 작업별 합산을 함께 작성한다. 기존 수량을 그대로 유지하도록 요청한 경우 `RETAINED`로 별도 표시하며 타당성을 새로 입증했다고 표현하지 않는다. 서버는 모든 필드가 기존 항목과 같은지 확인한다. 명백히 비현실적인 기존 수량도 검토 대상이다. 구현 범위(`QUOTATION`)와 조사·인용·정보 보호 등 과정 요구(`RESPONSE`)를 나누어 후자는 실제 조회 기록과 발화로 확인한다.

`EXCLUDED`에는 사용자 원문의 명시적인 제외 지시 인용이 필요하다. 초안 작성자가 요구된 기능을 임의로 제외한 경우 사용자 제외로 승인하지 않으며, 범위 누락 또는 근거 없는 제외로 반영을 차단한다. 부정 대조도 이 범위 결함을 실제로 검출했는지 확인한다.

## 한도와 실패

- 일반적인 3마리 대화: 조사 계획 1회 + 펫 3회 + 검증 1회. 검토 실패 후 한도가 남고 시간이 충분하면 보완 1회 + 새 검증 1회를 추가한다. 자동 보완은 한 번뿐이며 재검증 미완료·실패는 반영을 막는다. 조사가 불가능하면 계획 호출은 생략한다. 기존 요청의 모델·토큰·도구·시간·금액 한도를 넘기지 않는다.
- 수정한 발화는 원래 화자·답글 관계를 유지하고 “검토 후 정정”으로 표시한다. 수정 이벤트와 최종 저장 결과가 이전 스트리밍 발화를 덮어쓰며 재접속에서도 보존된다. 배포 시 새 프런트엔드와 백엔드 정책을 먼저 적용한 뒤 Agent를 교체한다.
- 근거가 떨어진 본문 여러 구간에 있으면 각 구간을 따로 인용·검사한다. 생략 부호로 합친 문자열이나 문서에 없는 문구는 통과시키지 않는다. 가정 항목에 붙인 출처도 검사하고 실제 웹 URL을 보존한다.
- 검토자는 원문을 다시 타이핑하는 대신 서버가 나눈 연속 본문의 번호를 선택할 수 있다. 서버가 해당 원문 구간을 직접 찾으며, 없는 번호·다른 출처·의미상 지지되지 않는 주장은 통과시키지 않는다. 작성자의 실제 확인 질문은 검토자의 보완 질문에 밀려 삭제되지 않는다.
- 보완자는 `KEEP`으로 현재 견적을 그대로 보존하고 발화만 수정할 수 있다. `REPLACE`는 전체 견적 교체, `DEFER`는 질문 우선 보류다. 어느 방식도 새로운 독립 검토를 생략하지 않는다. 접근성 자료는 필터 목록보다 키보드·대비 기준의 공식 상세 문서를 조회한다.
- 개인 API 키 실행은 별도 검증을 지원하지만 웹 조회는 기존 정책대로 차단한다. `document.read` 권한이 없으면 웹 조회하지 않는다.
- 공식 문서 직접 조회는 검색 크레딧을 쓰지 않으며 최대 2문서, 25초, 기존 다운로드 크기/리다이렉트/SSRF 제한을 따른다. `CONVERSATION_DOCUMENTATION_ENABLED=false`로 비활성화한다.
- Tavily는 기본 검색만 사용한다. 호출 전에 1크레딧 / 0.008 USD를 예약하고 시도 ID를 영속화한다. 취소·타임아웃·불확실한 응답에서도 예약을 지우지 않는다. 무료 월 한도를 가정하지 않는다. 모델 호출과 별도의 `externalToolCalls`로 보고하며 같은 시도의 반복 보고는 중복 정산하지 않는다.
- 검색·검증을 완료하지 못한 경우 상태를 명시한다. 검증 전 제안과 과거 검증 정보가 없는 제안은 새 대화에서 다시 검토해야 반영할 수 있다. 이미 반영한 기존 초안은 계속 조회·편집할 수 있다.

Tavily 요금 확인: [공식 크레딧 문서](https://docs.tavily.com/documentation/api-credits), 2026-10-22. 기본 검색의 공개 PAYG 상한을 사용한다. v3 예산은 기존 v2 모델 요율을 유지하며 유료 검색 승인을 추가한다. 이전 v1/v2 예약도 계속 읽는다. 외부 도구 원장은 별도 테이블에 보존하므로 이전 서버의 모델 원장 해석을 바꾸지 않는다. Agent가 먼저 교체되어도 이전 예산에서는 유료 검색을 시도하지 않으며 공식 문서 조회를 사용한다. 롤백에서는 새 버전의 금액을 모르는 이전 서버가 잔여 예약을 보수적으로 유지한다.

## 평가 기준

`agent/evaluation/pet-inquiries-v1.json`은 예약·결제·CSV·권한·Slack·DB 이전·모호한 범위·불가능한 일정·거짓 전제·접근성·개인정보·부분 수정 12종 합성 문의다. 실제 고객 데이터는 포함하지 않는다.

- 필수 개념: 견적 범위 또는 실제 확인 질문에서 100% 확인한다. 펫이 말로만 언급하면 반영으로 인정하지 않는다. 데이터셋 v1.1의 DB 이전 사례는 사용자의 “먼저 물어봐” 지시에 따라 초안 없이 데이터량·다운타임을 확인한다. 보류한 구현 요구는 원문 인용이 확인된 검토표의 QUESTION 항목으로 추적하며, 구현된 범위나 공수 점수로 표현하지 않는다.
- 공수: 사람이 정한 넓은 검토 구간과 작업별 독립 검증을 모두 통과한다. 구간은 시장 표준이나 확정 공수가 아니다. 시간은 평가상 8시간/일로 환산하며 날짜로 변환할 수 없는 FIXED 항목은 자동 합격으로 처리하지 않는다.
- 근거: 웹 조사 요구 사례는 실제 본문 조회와 별도 인용 검증이 필요하다. 출처 URL이 있다는 이유로 의미상 정확하다고 단정하지 않는다.
- 미정·불가능한 문의: 확인 질문을 남기고 확정된 전체 구현 견적을 만들지 않아야 한다.
- 부정 대조군: 범위 누락, 비현실적 공수, 검증 생략, 출처 누락이 합격하지 않는지 CI에서 확인한다. 이 검사는 모델 성능 점수가 아니다.
- 실제 모델 평가에서도 누락된 범위·비현실적인 공수·본문과 반대되는 인용을 넣은 3개 초안을 별도로 검사한다. 해당 결함을 실제 검토자가 판별해야 합격한다. 검증 호출 실패나 시간 초과를 오류 탐지 성공으로 세지 않는다.

실제 모델 평가는 다음처럼 명시적으로 실행한다. OpenAI 키와 필요 시 Tavily 키는 환경의 비밀 설정으로 제공하며 파일이나 로그에 복사하지 않는다. 상한은 호출 묶음당 0.20 USD이며 12종 문의와 3종 부정 대조를 합친 실행 전체 상한은 2.40 USD다. 유실된 사용량도 보수적으로 합산한다.

```powershell
$env:PYTHONPATH='src'
uv run python -m evaluation.pet_quality --live --model gpt-6-luna --output ../.tmp/pet-quality-live.json
```

Agent CI의 수동 실행에서 `live_pet_quality=true`를 선택하면 운영 컨테이너의 기존 키를 이용한다. 브랜치 소스를 임시 경로에만 풀어 실행하며 서비스 소스·설정·고객 DB를 바꾸지 않는다. 합성 결과를 CI 산출물에 보존하고 임시 파일을 정리한다. 자동 PR 검사에는 유료 호출이 없다. 이 평가는 운영자 승인 아래 실행하는 검사 비용이며 고객 계정의 견적 실행/저장과 별개다.

실제 결과의 의미와 출처를 사람이 함께 검토해야 한다. 동일 모델의 오류 상관관계, 유한한 평가 사례, 넓은 공수 구간, 공식 문서 라이브러리의 지원 범위가 남는 한계다. 통과 점수를 모든 문의에 대한 무오류 보장으로 표현하지 않는다. [OpenAI 평가 가이드](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 업무별 평가·부정 사례·사람 검토 원칙을 따른다.
