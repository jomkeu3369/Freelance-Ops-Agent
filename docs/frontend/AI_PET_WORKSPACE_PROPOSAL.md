# AI 펫 동료와 개인 API 키 연결 제품 개선 제안

> 기록일: 2026-09-12
> 상태: 사용자 요청에 따라 핵심 흐름 구현 진행. [구현 계획](AI_PET_IMPLEMENTATION_PLAN.md)과 [ADR-0030](../adr/0030-bounded-pet-advisors.md)을 기준으로 한다.
> 첫 배포: 기본 펫·실제 상태·공개 의견·견적 미리보기/반영. BYOK·생성 외형은 후속 단계다.

## 1. 배경과 방향

사용자는 현재 기능의 유용성에는 만족하지만 소비자 관점의 혁신성·참신함·재미가 부족하다고 판단했다. 설정의 `AI 사용 비용` 필요성에도 의문을 제기하고, 개인 API 키로 원하는 AI를 사용하는 방향을 제안했다.

이후 단일 결과만 제시하기보다 성향이 다른 캐릭터들이 “나라면 이렇게 한다”, “아니, 나는 이렇게 하겠다”라는 대안을 제시하고, 사용자가 캐릭터의 성향과 모습을 생성하는 경험을 제안했다. 외형과 존재감의 참고는 사용자가 언급한 **Codex의 펫처럼 생긴 작은 캐릭터들이 작업하는 모습**이다. 이 기록은 해당 기능의 기술 구조를 조사하거나 동일한 asset을 사용하기로 결정한 것이 아니다.

제품 경험의 중심 문장:

> 고객 문의를 넣으면 내가 꾸민 작은 AI 동료들이 자료를 살펴보고 각자의 대안을 제시한다. 나는 의견을 비교·조합해 내 견적을 완성한다.

### 논의의 확정 수준

- 사용자 제안 및 긍정한 방향: 여러 성향의 캐릭터, 서로 다른 의견, 성향·외형 생성, 작은 펫이 실제로 일하는 듯한 경험.
- 사용자 선호: 수동 AI 비용 설정의 필요성 재검토, 개인 API 키 연결.
- 아래 역할·화면 배치·MVP 순서·기술 접근은 대화에서 제안한 초안이며 상세 구현 확정 사항은 아니다.
- 요금제, 지원 모델, 펫 디자인, Agent 수와 실행 구조는 아직 결정하지 않았다.

## 2. 기존 기능을 더 쉽게 체감하는 흐름

현재 코드에는 핵심·권장·확장 견적안 비교, 근거 연결, 프로젝트 결과 회고가 있다. 등록과 관리 절차보다 가치를 먼저 경험하도록 다음 개선을 제안했다. 효과는 사용자 검증 전 가설이다.

| 개선 | 사용자 경험 | 기대 효과 |
|---|---|---|
| 문의로 바로 시작 | 고객 메시지를 붙여넣고 부족한 정보만 추가로 답변 | 첫 결과까지 입력 부담 감소 |
| 견적 변경 비교 | 기능을 빼거나 추가했을 때 범위·공수·금액 차이 확인 | 선택의 결과를 즉시 이해 |
| 추가 요청 대응 | 새 고객 요청을 기존 계약과 비교하고 추가 견적·답장 초안 제시 | 계약 이후 반복 사용 |
| 실제 수행 결과 반영 | 과거 유사 작업의 예상·실제 차이와 보정 제안 확인 | 사용할수록 나에게 맞는 견적 |

캐릭터 경험은 이 업무 흐름에 연결한다. 귀여운 움직임과 대화가 실제 견적 검토를 돕도록 한다.

## 3. 성향이 있는 펫 동료

### 역할 예시

| 캐릭터 예시 | 우선하는 가치 | 발언 예시 |
|---|---|---|
| 협상 담당 고양이 | 수익·계약 조건 | “가격을 낮추기보다 수정 횟수를 제한하자.” |
| 일정 담당 거북이 | 일정·납품 가능성 | “핵심 기능을 먼저 납품하고 나머지는 2차로 나누자.” |
| 근거 담당 부엉이 | 과거 사례·검증 근거 | “지난번 비슷한 작업에서 수정 대응이 더 오래 걸렸어.” |

이전 논의에서는 협상가 여우·현실주의자 거북이·장기 관계를 보는 전략가 부엉이도 예로 들었다. 동물과 역할의 결합은 고정 규칙이 아니며 사용자가 꾸미는 구조를 지향한다.

### 사용자 생성·꾸미기

- 외형과 개성: 이름, 동물 종류, 색상, 액세서리, 말투, 배경 설정.
- 자연어 생성 예시: “무뚝뚝하지만 내 수익을 챙겨 주는 검은 고양이.”
- 판단 성향 예시: 수익성↔관계 유지, 신속한 납품↔완성도, 보수적 범위↔도전적 제안.
- 성향은 제안의 우선순위와 선택 이유에 반영한다. 외모·말투만 다른 동일 답변을 반복하지 않는다.
- 생성 외형을 여러 동작에서 일관되게 유지하는 방법은 별도 설계한다. 기본 펫·공통 동작을 먼저 제공하고 생성 외형을 확장하는 방안이 제안됐다.

## 4. 의견 비교와 결과 적용

초기 상호작용 제안:

1. 고객 문의와 접근 가능한 프로젝트 자료를 준비한다.
2. 기본 펫 세 마리가 각자의 관점에서 핵심 제안 하나씩 제시한다.
3. 실제로 의견이 갈리는 핵심 쟁점에 한해 짧게 한 차례 반론한다.
4. 동의한 부분과 선택이 필요한 부분을 구분해 제안 카드로 보여준다.
5. 사용자가 `이 의견 적용`을 선택하면 작업 범위·조건·계산된 금액의 변경안을 미리 보여준다.
6. 사용자가 의견을 선택·조합한 뒤 견적에 반영한다.

합의가 있으면 그대로 표시하며 재미를 위해 억지 갈등을 만들지 않는다. 토론 전문을 기본 화면에 쌓지 않고 제안·근거·다음 행동을 우선한다. 공개 발언은 사용자용 판단 요약이며 비공개 chain-of-thought가 아니다.

단일 결과를 즉시 강요하지 않되, 최종적으로는 사용자가 선택한 하나의 업무 산출물로 정리할 수 있어야 한다.

## 5. 펫이 작업하는 화면

배치 초안은 중앙에 문의·견적, 하단에 작은 펫 작업 공간을 두는 것이다. 펫은 평소 조용히 작업하고 중요한 발견에 짧은 말풍선을 띄운다. 클릭하면 해당 근거와 제안을 펼친다. 최종 배치와 디자인은 아직 미확정이다.

| 실제 상태·사건 | 표현 예시 |
|---|---|
| 자료 조회 중 | 문서를 살펴보는 동작 |
| 제안 작성 중 | 책상에서 작업하는 동작 |
| 사용자 확인 필요 | 손을 들고 질문 표시 |
| 결과 준비 완료 | 제안 카드를 가져오는 동작 |
| 실패·취소·부분 완료 | 해당 상태와 재시도 또는 확인 행동 표시 |

움직임은 실제 실행 상태에 연결한다. 끝난 실행을 계속 작업 중으로 보이게 하거나 실패를 성공 연출로 가리지 않는다. 의견 카드의 작성 주체·상태가 실제 이벤트와 일치해야 한다.

접근성·집중 모드 상세는 후속 설계 과제다. `prefers-reduced-motion`, 키보드 접근, 펫 영역 접기와 모바일 축소 표현에서도 질문·근거·결과를 놓치지 않는 것을 수용 기준으로 제안한다.

## 6. AI 사용 비용 설정과 개인 API 키

현재 `settings/model-pricing-form.tsx`의 기능은 사용 한도 설정이 아니라 입력·출력·캐시 100만 토큰당 단가, 가격 버전, 유효 기간을 사용자가 등록하는 것이다. 일반 사용자에게는 운영 관리 부담에 가깝다는 판단을 공유했다.

| 구분 | 제안 |
|---|---|
| 일반 설정 | 수동 모델 단가 등록 화면 제거 또는 운영 관리 영역으로 이동 |
| AI 연결 | 기본 제공 AI / 내 API 키 사용 선택 |
| 연결 과정 | 제공사 선택 → 키 입력 → 연결 확인 → 지원 모델 선택 |
| 사용 내역 | 사용량과 산정 가능한 예상 비용을 읽기 전용 표시 |
| 내부 운영 | 비용 원장·가격 이력·실행 제한 유지 |

개인 API 키 연결(BYOK)은 선택권을 위한 기능이다. 이미 제공 사례가 있으므로 그 자체를 독자적인 혁신으로 주장하지 않는다. 참고: [OpenRouter BYOK 공식 문서](https://openrouter.ai/docs/guides/overview/auth/byok).

키 없이 체험하고 원하는 사용자는 자신의 키로 계속 쓰는 방안을 제안했다. 기본 제공 AI 유지 여부와 요금제는 미확정이다. 개인 키의 제공사 청구액과 서비스 사용료, 자체 산정한 예상 비용을 구분해야 한다.

개인 키는 서버 암호화 보관·조회 시 마스킹·교체·삭제 및 사용 권한을 설계한다. 브라우저 영구 저장소, 로그, Agent checkpoint에 원문을 남기지 않도록 해야 한다. 개인 소유 키를 workspace 내 누가 사용할 수 있는지, 실행·재개 시 키를 어떻게 전달·해결할지는 구현 전 결정할 사항이다.

‘원하는 AI’는 우선 도구 호출·구조화 출력 계약을 검증한 지원 모델에서 선택하는 의미로 구현하는 방안을 제안했다. 임의 모델·임의 endpoint 지원이나 캐릭터별 모델 선택은 아직 합의하지 않았다.

## 7. 기존 설계와의 관계

- Spring은 인증·workspace 권한·업무 데이터·견적 계산·비용 원장을 계속 소유한다.
- Python은 prompt·Agent 실행·HITL·모델 호출을 계속 소유하며 Spring 업무 테이블을 직접 읽지 않는다.
- 브라우저는 Spring 공개 API만 호출한다. 개인 키 연결도 이 경계를 유지한다.
- 캐릭터는 같은 권한 범위의 프로젝트 근거를 사용한다. 성격은 권한·안전 정책·사실·계산 결과를 바꾸지 않는다.
- 금액·세금·할인·합계는 Java Tool로 계산하고, 공수·일정 추정에는 근거 또는 가정을 연결한다.
- 발행 견적에 의견을 반영할 때는 기존 견적을 덮어쓰지 않고 새 revision을 만든다.
- provider/model을 실행마다 기록하고 조용한 fallback을 하지 않는다.
- 캐릭터 수와 독립 Agent 수는 동일할 필요가 없다. 독립 Agent 전체 실행을 캐릭터마다 복제하는 구조는 확정하지 않았다. 실행 비용·지연·품질을 비교해 결정한다.

관련 기준: [V2 명세](../V2_SPECIFICATION.md), [ADR-0010](../adr/0010-designer-first-frontend-vercel.md), [ADR-0021](../adr/0021-agent-audit-and-cost-ledger.md), [ADR-0026](../adr/0026-policy-controlled-ai-gateway.md).

기존 [VISUAL_DIRECTION.md](VISUAL_DIRECTION.md)는 차분한 업무 화면과 절제된 진행 표현을 강조한다. 펫의 존재감과 반복 동작은 이 시각 기준을 일부 재검토하는 방향이다. 이번 문서는 기존 기준을 수정하거나 Accepted ADR을 대체하지 않는다. 다음 세션에서 디자인 기준과 필요한 ADR을 먼저 정리한다.

## 8. 다음 세션 작업 제안

1. 이 문서와 최신 STATUS, 기존 디자인 지침·ADR, dirty worktree를 확인하고 다른 세션 변경을 보존한다.
2. 기본 펫 수·역할, 화면 배치, 생성 외형 범위, BYOK 소유권·지원 모델·기본 제공 정책을 구체화한다.
3. 필요한 ADR과 API 계약·permission·acceptance criterion을 구현 전에 작성한다.
4. 문의 하나에 펫 세 마리가 작업하고 각기 다른 제안 카드를 가져오는 첫 시제품을 만든다.
5. 제안 비교·변경 미리보기·견적 반영을 기존 Java 계산 및 revision 흐름과 연결한다.
6. 수동 단가 설정 정리와 BYOK 연결을 구현하고, 후속으로 생성 외형·추가 요청 대응·과거 결과 반영을 확장한다.

이 순서는 펫 논의까지 반영한 구현 제안이며 확정 일정은 아니다. 캐릭터 도입 전에는 수동 단가 설정 정리 → 문의 진입 → 견적 비교 → BYOK → 추가 요청 대응 순서를 제안했었다.

### 검증할 기준

- 각 의견의 차이가 말투뿐 아니라 범위·조건·우선순위에 드러나는가.
- 사용자가 근거를 확인하고 제안을 선택·조합할 수 있는가.
- 미리보기와 저장 결과의 금액이 서버 계산과 일치하는가.
- 펫의 실제 상태, 질문, 실패·부분 완료가 정확히 표현되는가.
- 개인 키의 사용자/workspace 격리, 삭제·교체, 비노출, 실패 처리가 검증되는가.
- 모델 호출 수·지연·비용 증가에 상한이 있는가.
- 첫 견적까지 걸린 시간, 실제 제안서 공유율, 재사용률이 개선되는가.

### 이번 기록의 검증 범위

대화 내용과 현재 관련 코드·문서를 바탕으로 작성했다. 앱 구현, 디자인 시제품, 이미지 생성, 실제 모델 호출, 사용자 실험은 수행하지 않았다. 기능이 구현됐거나 효과가 검증됐다는 의미로 해석하지 않는다.
