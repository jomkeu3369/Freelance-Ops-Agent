# Freelance Ops Agent 메인 페이지 디자인 브리프

> 대상: 웹 디자이너 · 제작 범위: 1920×1080 기준 메인 랜딩 페이지 · 반응형·세부 페이지·React 구현: 디자인 handoff 이후 구현 담당자 담당

## 1. 이 페이지가 해야 하는 일

메인 페이지의 역할은 기능을 많이 나열하는 것이 아닙니다. 방문자가 첫 화면에서 다음 세 가지를 이해하고, 요구사항 정리를 시작하도록 만드는 것이 목적입니다.

1. 이 서비스는 **한국 소프트웨어 개발 프리랜서**를 위한 업무 도구입니다.
2. 모호한 고객 문의를 요구사항·WBS·견적·제안서로 정리합니다.
3. AI 결과를 그대로 확정하지 않고 근거·가정·계산식과 사용자 검토를 함께 제공합니다.

이 제품을 “AI가 모든 일을 대신하는 자동화 서비스”로 표현하지 않습니다. Freelance Ops Agent는 프리랜서의 판단을 대신하는 서비스가 아니라, 판단에 필요한 자료와 다음 행동을 정리하는 의사결정 보조 도구입니다.

### 제품을 한 문장으로 설명하면

> 모호한 프로젝트 문의를 검증 가능한 WBS·견적·제안서로 바꾸고, 실제 수행 결과를 다음 견적의 근거로 축적하는 프리랜서 운영 서비스

### 방문자가 취할 행동

- 주요 행동: 고객 문의를 입력하고 요구사항 정리를 시작합니다.
- 보조 행동: 서비스가 어떤 순서로 작동하는지 확인합니다.

### 근거

- V2 명세 §1: 제품의 공식 정의
- V2 명세 §3.1: 구조화된 요구사항, 근거 기반 견적, 사용자 편집·승인
- V2 명세 §3.3: 첫 유료 검증 범위를 한국 소프트웨어 개발 프리랜서로 제한
- README Introduction: “얼마에, 며칠 안에 가능하냐”는 질문에서 시작된 실제 문제

## 2. 디자이너의 작업 범위

디자이너는 **1920×1080 기준 메인 페이지 한 개**를 제작합니다. 페이지 전체 길이는 섹션 구성에 맞게 확장할 수 있으며, 1920×1080은 첫 화면과 레이아웃을 검수하는 기준입니다.

디자이너가 담당하는 작업:

- 메인 페이지의 시각적 방향
- 섹션별 레이아웃과 정보 위계
- Hero 배경 그래픽과 제품 프리뷰
- 색상, 타이포그래피, 여백과 카드 스타일
- 핵심 이미지·아이콘·그래픽 원본
- 필요한 경우 모션 의도를 설명하는 메모

디자이너가 담당하지 않는 작업:

- 모바일·태블릿 반응형 시안
- 대시보드와 세부 애플리케이션 화면
- React·TypeScript 변환
- 실제 API 연결과 인증
- loading, error, empty 등 모든 제품 상태 구현

반응형과 세부 페이지는 승인된 메인 페이지의 시각 언어를 기준으로 구현 담당자가 확장합니다.

## 4. 전체 페이지 구성

페이지는 다음 순서로 읽혀야 합니다.

| 순서 | 섹션 | 방문자가 이해해야 하는 내용 |
|---:|---|---|
| 1 | Header | 제품의 주요 내용과 시작 지점 |
| 2 | Hero | 누구를 위한 어떤 서비스인지 |
| 3 | 문제 제시 | 기존 견적 업무가 왜 어려운지 |
| 4 | 작동 방식 | 문의가 어떤 순서로 결과가 되는지 |
| 5 | 결과물 | 사용자가 실제로 무엇을 얻게 되는지 |
| 6 | 근거와 사용자 검토 | 일반 AI 답변과 무엇이 다른지 |
| 7 | 실제 결과의 재사용 | 사용할수록 다음 견적이 어떻게 개선되는지 |
| 8 | 첫 출시 대상 | 현재 누구에게 집중하는지 |
| 9 | 최종 CTA | 다음 행동 |
| 10 | Footer | 제품 및 정책 링크 |

아래부터는 모든 섹션을 같은 형식으로 설명합니다.

- **목적**: 왜 필요한 섹션인가
- **들어갈 내용**: 화면에 무엇을 배치하는가
- **확정 문구**: 시안에 실제로 사용할 문구
- **시각 방향**: 어떻게 보여줄 것인가
- **근거**: 어떤 제품 문서에서 나온 내용인가

## 5. 섹션별 상세 명세

### Section 1. Header

#### 목적

방문자가 페이지의 주요 내용을 빠르게 탐색하고, 언제든 요구사항 정리를 시작할 수 있게 합니다.

#### 들어갈 내용

- 왼쪽: 임시 워드마크 `Freelance Ops`
- 가운데: 섹션 이동 메뉴
- 오른쪽: 로그인과 주요 CTA

#### 확정 문구

메뉴:

- `제품 소개`
- `작동 방식`
- `검증 원칙`
- `대상 사용자`

오른쪽 버튼:

- 텍스트 버튼: `로그인`
- 주요 버튼: `요구사항 정리 시작하기`

가격은 아직 가설 단계이므로 Header에 `가격` 메뉴를 넣지 않습니다.

#### 시각 방향

- 검은 배경 위의 얇고 단정한 내비게이션
- 왼쪽 워드마크, 가운데 메뉴, 오른쪽 주황색 CTA
- 지나치게 둥근 캡슐형 메뉴보다 얇은 선과 적당한 여백을 사용
- 로고가 확정되지 않았으므로 별도 심볼을 새로 만들지 않고 워드마크로 처리

#### 근거

- V2 명세 §3.3: 가격은 검증되지 않은 수익화 가설
- V2 명세 §13.1: 실제 업무 도구처럼 보이는 시각 원칙

### Section 2. Hero

#### 목적

첫 5초 안에 대상 사용자, 해결하는 문제와 결과를 전달합니다.

#### 들어갈 내용

- 작은 상단 라벨
- 한 문장의 메인 제목
- 두 줄 이내의 설명
- 주요 CTA와 보조 CTA
- 주황색 발광 링
- 서비스 사용 흐름을 축약한 제품 프리뷰

#### 확정 문구

상단 라벨:

`AI-POWERED FREELANCE OPERATIONS`

메인 제목:

> 모호한 고객 문의를, 근거 있는 견적으로.

설명:

> 고객 문의에서 요구사항과 불확실성을 정리하고, 확인 질문·WBS·견적·제안서로 연결합니다.

버튼:

- 주요 CTA: `요구사항 정리 시작하기`
- 보조 CTA: `작동 방식 보기`

CTA 아래 보조 문구:

`AI 초안은 사용자가 검토하고 확정합니다.`

#### Hero 제품 프리뷰에 들어갈 내용

제품 프리뷰는 통계 대시보드가 아니라 다음 흐름을 보여줍니다.

```text
고객 원문 → AI 요구사항 초안 → 확인 질문 → 견적 준비
```

프리뷰용 예시:

- 프로젝트: `브랜드 사이트 리뉴얼`
- 현재 상태: `정보 확인 중`
- 확인된 요구사항: `7개`
- 확인이 필요한 항목: `3개`
- 연결된 근거: `4개`
- 표시된 가정: `2개`

이 숫자는 시안용 예시 데이터이며 제품 성능이나 실제 사용자 통계가 아닙니다.

#### 시각 방향

- 제목과 설명은 화면 중앙에 배치
- 주황색 발광 링은 Hero 하단에서 제품 프리뷰를 감싸도록 배치
- 프리뷰는 화면 아래에서 위로 떠오르는 깊이감을 사용
- 화면 뒤의 대형 글자나 그리드는 낮은 대비로만 사용
- 제목과 CTA보다 배경 효과가 강해지지 않게 조절

#### 근거

- V2 명세 §1: 모호한 문의를 WBS·견적·제안서로 전환
- V2 명세 §3.1: 기능 목록과 불확실성 구조화
- V2 명세 §13.2 Project Intake: 원문, 추출 결과, 누락 질문과 diff
- V2 명세 §13.1: AI 생성 결과와 사용자 확정 결과 구분

### Section 3. 문제 제시

#### 목적

방문자가 자신의 문제를 발견하고, 왜 기존 방식만으로는 부족한지 이해하게 합니다.

#### 들어갈 내용

세 개의 문제 카드와 짧은 설명을 배치합니다.

#### 확정 문구

섹션 라벨:

`WHY IT MATTERS`

섹션 제목:

> 견적이 어려운 이유는 가격표가 없어서가 아닙니다.

설명:

> 고객의 말 속에서 범위, 일정, 위험과 빠진 정보를 동시에 판단해야 하기 때문입니다.

카드 1:

**요구사항이 불완전합니다**

“반응형으로 만들어 주세요”라는 한 문장만으로는 화면 수, 관리자 기능과 운영 범위를 알 수 없습니다.

카드 2:

**견적의 근거가 흩어져 있습니다**

과거 프로젝트, 단가표, 작업 경험과 외부 자료를 매번 따로 찾아야 합니다.

카드 3:

**AI 답변도 그대로 믿을 수 없습니다**

출처, 계산식과 가정이 보이지 않으면 빠른 답변도 실제 거래에는 사용하기 어렵습니다.

#### 시각 방향

- 동일한 크기의 카드 세 개
- 카드마다 문서 조각, 연결선, 경고 표시처럼 단순한 그래픽 사용
- 로봇, 뇌, 마법봉 아이콘은 사용하지 않음
- 카드의 핵심 단어만 주황색으로 강조

#### 근거

- README Introduction: 가격·기간을 감으로 결정해야 했던 실제 문제
- V2 명세 §2: 평가 부재, 근거 추적 불가, 자유 텍스트 계산 문제
- V2 명세 §10.3: source·수치·계산식·assumption을 사용자에게 표시

### Section 4. 작동 방식

#### 목적

서비스를 사용하면 어떤 순서로 일이 진행되는지 보여줍니다. Agent 내부 구조보다 사용자의 업무 흐름을 설명하는 섹션입니다.

#### 들어갈 내용

다섯 단계를 하나의 연결된 흐름으로 보여줍니다.

#### 확정 문구

섹션 라벨:

`FROM INQUIRY TO PROPOSAL`

섹션 제목:

> 한 번의 문의가, 검토 가능한 제안서가 됩니다.

1. **문의 등록** — 고객의 메시지를 붙여넣거나 요구사항 문서를 등록합니다.

2. **요구사항 정리** — 목표, 기능, 일정, 예산, 제약과 빠진 정보를 구분합니다.

3. **확인 질문** — 견적 전에 반드시 확인해야 할 질문을 우선순위로 제안합니다.

4. **WBS·견적 작성** — 작업 항목별 공수와 금액을 계산하고 범위별 시나리오를 비교합니다.

5. **검토·제안** — 프리랜서가 초안을 수정하고 확정한 뒤 고객에게 제안서를 전달합니다.

섹션 하단 문구:

`중요한 단계마다 사용자의 확인을 기다립니다.`

#### 시각 방향

- 다섯 단계를 발광 링과 연결된 하나의 경로로 표현
- 현재 단계만 주황색, 완료 단계는 밝은 회색, 대기 단계는 어두운 회색
- 각 단계 사이에 화살표보다 흐르는 빛 또는 얇은 선을 사용
- 시스템 내부 Agent 이름, LangGraph, Tool 이름은 메인 페이지에 노출하지 않음

#### 근거

- V2 명세 §3.1: 문의 구조화, Tool 조회, WBS 계산, 사용자 편집과 제안서 제공
- V2 명세 §9.2: clarification·risk·estimation·approval 상태 흐름
- V2 명세 §13.2: Project Intake, Quote Builder, Proposal Preview
- V2 명세 §13.1: dense dashboard보다 guided workflow 우선

### Section 5. 사용자가 받는 결과물

#### 목적

추상적인 “AI 분석”이 아니라 실제 거래에 사용할 수 있는 산출물을 보여줍니다.

#### 들어갈 내용

세 개의 결과물 카드를 배치합니다.

#### 확정 문구

섹션 라벨:

`DELIVERABLES`

섹션 제목:

> 대화가 아니라, 실제 업무에 사용할 결과를 만듭니다.

카드 1:

**요구사항 명세**

기능, 제약, 일정, 예산, 누락 정보와 확인 질문을 구조화합니다.

표시할 작은 항목:

- `확정된 요구사항`
- `확인 필요`
- `제외 범위`

카드 2:

**범위별 견적안**

필수 범위, 권장 범위와 확장 범위를 비교하고 각 안의 공수·금액·가정을 보여줍니다.

표시할 시나리오:

- `Lean`
- `Recommended`
- `Expanded`

카드 3:

**고객 전달용 제안서**

범위, 금액, 일정, 지급 조건, 가정과 제외 사항을 한 문서로 정리합니다.

표시할 행동:

- `미리보기`
- `PDF 내보내기`
- `승인 요청`

#### 시각 방향

- 카드마다 실제 문서 일부를 축약한 미니 프리뷰 사용
- 단순 아이콘만 놓지 말고 산출물의 구조가 보이게 제작
- `Recommended`만 주황색으로 강조하되 선택을 강요하는 표현은 피함

#### 근거

- V2 명세 §3.1: 최소안·추천안·확장안 비교와 제안서 제공
- V2 명세 §11.1: schema 기반 WBS와 견적 초안
- V2 명세 §11.2: Lean·Recommended·Expanded 시나리오
- V2 명세 §13.2: Quote Builder와 Proposal Preview 구성

### Section 6. 근거와 사용자 검토

#### 목적

Freelance Ops Agent가 일반 생성형 AI와 다른 핵심 이유를 설명합니다.

#### 들어갈 내용

왼쪽에는 견적 항목, 오른쪽에는 해당 항목의 근거 Drawer를 보여주는 제품 프리뷰를 배치합니다.

#### 확정 문구

섹션 라벨:

`EVIDENCE BEFORE CONFIDENCE`

섹션 제목:

> 빠른 답변보다, 설명 가능한 결과를 우선합니다.

설명:

> 견적에 사용한 자료, 반영한 수치, 계산식과 확인되지 않은 가정을 함께 보여줍니다.

네 가지 원칙:

**출처**

과거 프로젝트, 단가표, 정책 문서 등 사용된 자료를 연결합니다.

**계산**

공수, 단가, 할인, 세금과 합계가 어떻게 계산됐는지 보여줍니다.

**가정**

확인되지 않은 내용은 사실처럼 숨기지 않고 별도로 표시합니다.

**사용자 확정**

AI 초안은 프리랜서가 수정하고 승인한 뒤에만 최종 결과가 됩니다.

제품 프리뷰 예시:

```text
작업 항목       포트폴리오 관리 기능
예상 공수       5–7일
근거            유사 완료 프로젝트 2건
적용 단가       사용자 Backend 단가표 v2
가정            이미지 최적화는 기본 수준
상태            사용자 확인 필요
```

#### 시각 방향

- 견적 항목과 근거를 선으로 연결
- `근거`, `가정`, `사용자 확인 필요`를 서로 다른 색과 태그로 구분
- 근거가 있다는 이유로 “정답”, “100% 정확”과 같은 표현을 사용하지 않음
- 법률·정책 관련 요소에는 출처와 기준일이 보이는 형태를 사용

#### 근거

- V2 명세 §2: Evidence Ledger와 결정적 계산 도입 이유
- V2 명세 §10.3: source, 수치, 계산식, assumption과 신뢰 범위 표시
- V2 명세 §11.3: HIGH/MEDIUM/LOW와 공수 범위로 confidence 표현
- V2 명세 §16.4: 법률·정책 근거에 source, version과 시행일 표시
- V2 명세 §9.3: 비공개 chain-of-thought를 노출하지 않고 source·계산식·assumption을 제공

### Section 7. 실제 결과의 재사용

#### 목적

프로젝트가 끝난 뒤 기록한 실제 결과가 다음 견적의 품질을 높인다는 장기 가치를 설명합니다.

#### 들어갈 내용

이전 견적, 실제 수행 결과와 다음 견적이 연결되는 순환 구조를 보여줍니다.

#### 확정 문구

섹션 라벨:

`OUTCOME-INFORMED ESTIMATION`

섹션 제목:

> 끝난 프로젝트가, 다음 견적의 근거가 됩니다.

설명:

> 예상 공수와 실제 공수, 계약 금액과 범위 변경을 기록해 이후 유사 프로젝트의 참고 사례로 사용합니다.

세 단계:

- `견적 확정`
- `실제 결과 기록`
- `다음 견적에서 참고`

주의 문구:

`AI가 스스로 학습한다는 의미가 아니라, 사용자가 승인한 실제 결과를 검색 근거로 재사용합니다.`

#### 시각 방향

- Hero의 주황색 링을 다시 사용해 순환 구조를 표현
- “학습하는 뇌” 이미지 대신 견적서와 Outcome 기록이 연결되는 모습 사용
- 예상과 실제의 차이를 작은 비교 막대나 숫자 차이로 표현

#### 근거

- V2 명세 §2: `continual learning` 대신 `Outcome-informed retrieval` 사용
- V2 명세 §3.1: 실제 공수와 금액을 다음 검색 근거로 사용
- V2 명세 §8 Outcome: 완료 결과를 승인된 과거 사례로 활용
- V2 명세 Phase 5: 실제 공수 회고와 calibration 측정

### Section 8. 첫 출시 대상

#### 목적

지원 범위를 과장하지 않고, 현재 누구의 문제를 먼저 해결하는지 분명히 합니다.

#### 들어갈 내용

한국 소프트웨어 개발 프리랜서의 대표 업무를 보여주는 짧은 설명과 직무 태그를 배치합니다.

#### 확정 문구

섹션 라벨:

`BUILT FOR THE FIRST REAL WORKFLOW`

섹션 제목:

> 먼저, 한국 소프트웨어 개발 프리랜서의 견적 업무부터 해결합니다.

설명:

> 웹·앱·자동화 프로젝트의 요구사항 정리, 작업 범위 산정과 고객 제안 흐름을 우선 검증합니다. 다른 직군과 해외 거래는 검증된 도메인·관할권 기준을 갖춘 뒤 단계적으로 확장합니다.

직무 태그:

- `Frontend`
- `Backend`
- `Full-stack`
- `Mobile`
- `Automation`

#### 시각 방향

- 사람 얼굴을 나열하는 스톡 사진보다 개발 업무의 산출물과 흐름을 보여줌
- 코드 화면을 과도하게 강조하지 않고 견적·일정·범위 문서를 중심으로 구성
- “모든 프리랜서 지원”과 같은 문구는 사용하지 않음

#### 근거

- V2 명세 §3.3: 첫 유료 검증 범위를 한국 소프트웨어 개발 프리랜서로 제한
- V2 명세 §10.5: 첫 domain/jurisdiction pack도 동일 범위로 제한
- V2 명세 Phase 6: 실제 유료 사용과 중단 사유를 기록한 뒤 확장

### Section 9. 최종 CTA

#### 목적

페이지를 읽은 방문자가 부담 없이 첫 행동을 시작하게 합니다.

#### 들어갈 내용

- 짧은 제목
- 한 문장의 설명
- 주요 CTA 하나
- 서비스 원칙을 보여주는 짧은 보조 문구

#### 확정 문구

제목:

> 다음 고객 문의부터, 더 명확하게 시작하세요.

설명:

> 요구사항을 정리하고, 확인할 질문을 찾고, 근거 있는 견적의 첫 초안을 만들어 보세요.

버튼:

`요구사항 정리 시작하기`

버튼 아래 문구:

`초안은 언제든 수정할 수 있으며, 사용자의 확인 없이 확정되지 않습니다.`

#### 시각 방향

- Hero의 주황색 조명을 다시 사용해 페이지의 시작과 끝을 연결
- CTA는 하나만 강하게 강조
- 가격 할인, 마감 임박, 가짜 희소성 표현은 사용하지 않음

#### 근거

- V2 명세 §3.1: 사용자가 AI 결과를 편집하고 승인
- V2 명세 §3.3: 무료 요구사항 명확화는 가설이지만 가격과 한도는 미확정
- V2 명세 §17.4: 무제한 사용과 silent 과금 금지

## 6. Hero 배경과 이미지 제작 지침

Hero에는 사진보다 추상 그래픽을 우선합니다. 어두운 흑연색 배경 위에 주황색 또는 호박색의 빛이 제품 프리뷰를 감싸는 형태를 사용합니다.

발광 링은 완전한 원보다 일부가 열린 궤도 형태가 좋습니다. 제목과 CTA를 가리지 않고, 화면 아래에서 제품이 드러나는 깊이감을 만들어야 합니다.

그래픽 제작 참고 키워드:

```text
dark graphite background, amber orange luminous orbit, soft volumetric light,
subtle glass surface, premium SaaS landing page, low contrast,
no text, no logo, no human face, no robot, no stock photo look
```

사진을 사용해야 한다면 Hero가 아닌 보조 영역에 제한합니다. 어두운 작업 공간, 노트북, 메모와 견적서를 정리하는 손처럼 프리랜서의 실제 업무가 느껴지는 장면이 적합합니다. 얼굴, 개인정보와 실제 고객 문서는 포함하지 않습니다.

## 7. 기본 시각 시스템

### 색상

- 전체 배경: `#050708`
- 카드·제품 표면: `#101316`
- 주황색 강조: `#FF7A18`
- 밝은 주황색: `#FFB15C`
- 기본 텍스트: `#F5F7FA`
- 보조 텍스트: `#98A1AA`
- 경계선: `rgba(255,255,255,0.12)`

정확한 색상값은 디자이너가 조정할 수 있습니다. 주황색은 AI의 신비함보다 현재 단계, 확인할 내용과 다음 행동을 강조하는 데 사용합니다.

### 타이포그래피

- 한국어: Pretendard Variable
- 영문·숫자: Geist 또는 Pretendard Variable
- Hero 제목: 72–96px 범위에서 2줄 이내
- 섹션 제목: 44–56px 범위
- 본문: 18–20px 범위
- 설명 문장은 한 문단당 2–3줄을 넘기지 않음

### 카드와 제품 프리뷰

- 배경과 충분히 구분되는 어두운 표면
- 얇은 경계선과 제한된 그림자
- 정보 상태는 색상만이 아니라 텍스트 태그로도 구분
- 제품 프리뷰 안의 글자가 장식처럼 너무 작아지지 않게 구성

## 8. 모션 방향

디자이너가 모션을 완전히 구현할 필요는 없습니다. 최종 구현자가 이해할 수 있도록 연출 의도를 메모로 남겨주세요.

- Hero 발광 링은 느리게 회전하거나 밝기가 미세하게 변합니다.
- 스크롤하면 제품 프리뷰가 아래에서 올라옵니다.
- 작동 방식의 다섯 단계는 순서대로 강조됩니다.
- 근거 Drawer는 견적 항목을 선택했을 때 연결 관계가 보입니다.
- 버튼은 크기 변화보다 색상과 밝기 변화로 반응합니다.

실제 애니메이션, 키보드 접근성과 reduced-motion 처리는 구현 담당자가 React 구현 단계에서 담당합니다.

## 9. 사용하면 안 되는 콘텐츠

아직 검증되지 않은 항목은 디자인의 빈 공간을 채우기 위해 만들지 않습니다.

- 가짜 고객 후기
- 존재하지 않는 고객사 로고
- `98% 정확도`, `10배 빠름` 같은 미검증 수치
- 확정되지 않은 가격표와 할인율
- “모든 직군·모든 국가 지원” 문구
- “AI가 알아서 계약을 완료한다”는 표현
- “사용할수록 모델이 자동 학습한다”는 표현
- 법률 판단을 대체한다는 표현
- 무제한 AI 사용 문구

비어 보이는 영역은 가짜 사회적 증거보다 제품 프리뷰, 실제 워크플로우와 검증 원칙으로 채웁니다.

## 10. 디자이너 handoff 목록

최종 전달물에는 다음 항목을 포함해 주세요.

- 1920×1080 기준 메인 페이지 전체 시안
- 편집 가능한 원본 파일 또는 가능한 경우 HTML·CSS·JavaScript
- Hero 발광 링과 제품 프리뷰 원본 에셋
- 아이콘, 폰트와 이미지 라이선스 목록
- 색상, 글꼴 크기, 여백과 카드 규칙
- 섹션별 사용 문구
- 주요 모션의 시작·종료 상태를 설명한 메모

반응형, 세부 페이지와 React component 분리는 handoff 이후 구현 담당자가 담당합니다.

## 11. 최종 검수 질문

다음 질문에 모두 “예”라고 답할 수 있어야 합니다.

- 첫 화면에서 프리랜서를 위한 서비스임을 알 수 있는가?
